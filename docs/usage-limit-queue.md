# Usage Limit 中の入力キュー

Claude / Codex が利用制限を通知したセッションでは、以降の `input` を
既存の1件キューに保持する。`delivery: steer` や delivery 未指定でもキューが優先される。
既に次ターン待ちの入力がある場合も、その入力を制限解除まで保持する。
制限に到達した元の作業自体は自動再実行しない。Codex の自動復帰設定とは別の機能であり、
ユーザーのキュー入力がある場合は自動復帰を取り消して二重送信を防ぐ。

## 検出と解除

- Claude: SDK の `rate_limit_event.status = rejected` と assistant の `error = rate_limit`。
  構造化通知の解除時刻を優先し、時刻がない場合は既存 Query の usage API で補完する。
  補完対象は共通5h/7d枠と現在のモデルに対応する枠。warning / allowed からは制限を推測しない。
- Codex: `turn/start` の拒否と実行中ターンの終端失敗。上流が再試行中の通知は対象外。
  エラーの解除時刻を読み、`account/rateLimits/read` の使い切った枠で補完する。
- 解除時刻になったら利用状況を再確認する。まだ制限中なら新しい時刻まで保持する。
  時刻不明・利用状況取得失敗では入力を送らず、60秒後に再確認する。
  取得は10秒で打ち切り、古い確認結果が新しい拒否通知を上書きしないよう管理する。
- 解除確認後も別ターンや承認処理の最中なら次の `input_ready` まで待つ。
  タイマーは Node の上限を超えない長さに分割する。

## プロトコルとUI

既存の `conversation_queue.items[]` とセッションの `queuedInput` に任意フィールドを追加する。

- `waitingForUsageLimit`: 利用制限待ち
- `retryAt`: 解除予定のISO日時（不明の場合は省略）
- `clientMessageId`: 対応するローカル送信を識別するID

アプリは解除予定時刻、または時刻確認中を表示し、差し込み操作を隠す。
編集・取消は既存の操作を使う。待機中の入力はキューパネルに置き、
Bridge管理キューのIDに一致する楽観表示だけを取り除く。
Claude SDK内部の `queued: true` ACKだけではバブルを削除しない。

新しいクライアントメッセージは追加しない。古いアプリは追加フィールドを無視し、
従来のキュー表示のまま待機できる。新アプリ＋古いBridgeは従来の次ターンキューとして動作する。

## ライフサイクル

タイマーはBridgeが管理するため、アプリの切断・バックグラウンド移行には依存しない。
再接続では既存のセッションスナップショットから待機情報を復元する。
キュー取消・セッション停止／終了・破棄ではタイマーも破棄する。
既存キューと同様、Bridge再起動をまたぐ永続化と、別セッションへの制限状態の伝播は行わない。
