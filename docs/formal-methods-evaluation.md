# 形式手法の試行レポート: Bridge の権限承認フロー

2026-11-24 実施。Bridge の Claude 用プロセス（`packages/bridge/src/sdk-process.ts`）の権限承認フローを、FSL・Quint・TLA+ の3つで同じ出題のもとに検証し、効果を比べた。

目的は、形式手法がこのコードベースで役に立つか、どこで使うべきかを知ること。

> **その後**: この比較を受けて Quint を採用し、見つかった疑いのうち7件を直した。経過は末尾の「[採用後](#採用後)」に書いた。「結論」から「再現方法」までは比較時点（コミット `5d75b6f0`）の記録で、行番号もその時点のもの。

## 結論

- **効果はあった。** 3,661行の既存テスト（`sdk-process.test.ts`）が通っているコードから、3ツールとも同じ8件の「不具合の疑い」を独立に挙げた。どれも実際の `SdkProcess` クラスに同じイベント列を流して再現できた。
- **ただし確定した不具合はまだ0件。** 8件のうち3件は「本物の SDK がそのイベント順を出すか」に依存し、そこは確かめていない。残り5件はクラス単体では起きるが、利用者に見える害までは追っていない。
- **効いたのは全探索よりも、性質を書いたこと。** 安全性の反例はすべて3〜7ステップと短く、Quint のランダム実行だけでも全部見つかった（流し直した1件は約2秒）。「保留があるなら状態は `waiting_approval`」のような当たり前の一文を書き、SDK が送りうるイベントを列挙した時点で、既存テストが試していない順序が出てきた。
- **全探索が効いたのは3か所。** 「成立する」と言い切ること（P2・P6）、活性（P7・P8）、原因の切り分け（仮の修正を全部入れると全性質が通る）。
- **ツールの差は、見つかるものより手間に出た。** 見つけた内容はほぼ同じ。違ったのは、仕様が通るまでの往復回数、活性の扱い、仕様と実装をつなぐ手段。
- **FSL のテスト雛形生成は、今回は役に立たなかった。** 反例を手でテストに起こすほうが有用だった。

## やったこと

1. 検証範囲と、確かめたい性質9つ（P1a〜P8）を先に文書にした（[SCOPE.md](../formal/permission-flow/evaluation/SCOPE.md)）。性質はコードの現状ではなく意図から書いた。
2. 3つのエージェントに同じ文書だけを渡し、互いの成果物を見せずに、コードを読んで仕様を書かせた。
3. 仕様が空振りしていないかを確かめるため、過去の不具合2つと現行のガード外し1つ（M1〜M3）をモデルに仕込み、検出できるかを見た。
4. 出てきた反例を、SDK の `query` だけ差し替えた実際の `SdkProcess` に流して再現を確かめた。
5. エージェントの報告をうのみにせず、各ツールの主要な検証と再現テストを流し直した（後述）。

対象は `SdkProcess` の状態、保留中の承認、入力キュー、権限モード変更。Codex・Antigravity、WebSocket 層、アプリは対象外。

## 見つかった不具合の疑い

3ツールの反例を原因ごとにまとめ直した。行番号は `packages/bridge/src/sdk-process.ts`。

疑い8は分類が割れた。Quint と TLA+ の担当は「一時的な不具合の疑い」、FSL の担当は「設計どおり」としている。疑い7は扱いが割れた。Quint の担当は SDK 次第の反例として普通に報告し、FSL と TLA+ の担当は、既定では切ってある仮定を足したときだけ出る参考結果としている。

不具合ではないと判断したもの:

- **二重の `resolve`（P3）**: 中止済みシグナルと同期リスナーの即答が重なると `resolve()` が2回呼ばれる。Promise は2回目を無視するので実害はなく、同期で答える呼び出し元も本番コードにない。
- **一括拒否で `permission_resolved` を出さない（P4）**: `result`・`stop`・再開始での挙動。`sdk-process.test.ts:3346` が固定している設計で、アプリは `idle` を見て表示を消す。

### 確かめたことと、確かめていないこと

- **確かめた**: 8件とも、実際の `SdkProcess` に同じイベント列を流すと、モデルと同じ状態になる。
- **確かめた**: 疑い1に関して、`system` フレームはサブエージェント由来かどうかの振り分け（`:1958`）を通らない。振り分けが見るのは `assistant`・`user`・`stream_event` だけ。
- **確かめた**: 疑い1のアプリ側の影響。`apps/mobile/lib/features/chat_session/permission_transcript.dart:65` は、状態が `waiting_approval` でなければ、アクティブな1件以外の保留要求を解決済みとして扱う。承認が2件並んでいるときに状態が `running` に変わると、2件目の承認ボタンが消える筋がある。
- **確かめていない**: 本物の SDK が疑い1・5・7のイベント順を実際に出すか。
- **確かめていない**: WebSocket 層やアプリを通したときに、利用者に見える害になるか。
- **エージェントの報告のみ**: 疑い2の「CLI の取り消し要求で中止シグナルが発火する」、疑い6の「再開始の窓が実在する」は、Quint 担当のエージェントが SDK のソースを読んで確認したと報告している。私は読み直していない。

## 反例を1つ追う（疑い1）

性質 P1a は「保留中の承認要求があれば、状態は `waiting_approval`」。

`updateStatusFromMessage`（`:2666`）で、`assistant` と `user` のフレームは保留表が空かを確かめてから `running` にする（`:2682`、`:2688`）。`system` の status フレームだけ、その確認がない（`:2671-2676`）。

TLA+ が出した最短の反例は次の並びだった。

1. セッション開始、入力を送ってターンが始まる。
2. SDK が `canUseTool` を呼ぶ。保留表に1件入り、状態は `waiting_approval`。
3. SDK が `system` の `status: compacting` を送る。
4. 状態が `compacting` に変わる。保留表には1件残ったまま。

既存テストは status フレームによる状態の変化そのものは確かめているが（`sdk-process.test.ts:2160` 付近）、承認待ち中に届く場合は試していなかった。人が思いついた順序はテストに書かれていて、思いつかなかった順序が残っていた、という形になっている。

3つの仕様では、同じ箇所が次のように書かれている。

```text
// FSL
action sdk_status_compacting() {
  requires hasQuery and not stopped and sdkInflight > 0
  status = Compacting          // コードには保留の確認がない
}
invariant P1a_PendingImpliesWaiting {
  (announcing == none and pend.size() > 0) => status == WaitingApproval
}
```

```text
// Quint
pure def systemP(st: State, kind: str): State =
  if (kind == "compacting") setStatus(st, "compacting")
  else if (kind == "requesting") setStatus(st, "running")
  else if (st.status == "compacting") setStatus(st, "running")
  else st
val P1a = s.pending != Set() implies s.status == "waiting_approval"
```

```text
\* TLA+
SysStatus(s) ==
    /\ query = "live" /\ sdkTurn = "active"
    /\ \/ s = "compacting" /\ status' = "compacting"
       \/ s = "requesting" /\ status' = "running"
       \/ s = "null" /\ status = "compacting" /\ status' = "running"
P1a == Quiet => (pending # {} => status = "waiting_approval")
```

（FSL と TLA+ の抜粋は、原因の切り分け用のスイッチを省いている。）

### FSL

- **よかった点**: 帰納法で深さ無制限の証明ができた（P2・P6 と、仮の修正を全部入れたモデルの全安全性）。結果が JSON で返るので、エージェントが反例をそのまま読める。`mutate` で仕様の空振りを数値で見られる。
- **つまずいた点**: 手続きの再利用がなく、一括拒否の処理を8か所に写した。`verify` は最初に破れた性質で止まるので、性質ごとに回し直す。相互に依存する補題は `--lemma` では通らず、仕様に入れる必要があった。帰納法には補助の不変条件が7つ要った。
- **活性**: `leadsTo` と `fair` は書けるが、有界検査まで。深さ無制限の証明は `helpful_action_not_enabled` で失敗した。
- **変異解析**: スコアは 0.33（892件中292件を検出）。ただし成立する性質だけで、深さ4で回した値。生き残りの多くは、現行コードが破っているため外した性質が見るはずの変数に集中している。
- **テスト雛形の生成**: `testgen` は518行の vitest 雛形を出したが、使わなかった。組み込みの100ステップのランダム走行は承認待ちに一度も到達せず、`observe()` が返すべき23変数のうち8つは実装に対応物がなく、アダプタは同期 API なのに `setPermissionMode` は非同期。アダプタの接続までは試していないので、「使えない」ではなく「割に合わないと判断した」が正確。
- **試していない機能**: 業務・要件・設計の3層を refinement でつなぐ機能。今回は設計層1枚だけで、FSL の主な売りの1つは評価できていない。

### Quint

- **よかった点**: 仕様が TypeScript に近く、往復が3回で済んだ。ランダム実行（2万本×25ステップ）が安全性の反例をすべて見つけた。流し直した P1a の1件は約2秒だった。`--mbt --out-itf` で出したトレースを実装に流す仕組みがそのまま動いた。現行モデルの500本は実装と全部一致し、退行モデルのトレースは食い違った。
- **つまずいた点**: 既定のモデル検査器 Apalache が使えなかった。深さ4の反例に15分かけてもタイムアウトした。全探索の結果はすべて TLC バックエンドによる。TLC バックエンドは ITF を書き出さず、複数の不変条件を渡すとどれが破れたかを言わない。
- **独自の工夫**: SDK のふるまいを切り替えられる仮定に分けたので、「どの仮定のもとで破れるか」が表で読める。P1b と P4 はどの仮定でも破れ、P1a・P5・P7・P8 は SDK 次第、と切り分けられた。

### TLA+

- **よかった点**: 最初に終わり、全探索と活性の両方が素直に動いた。公平性の仮定を1つずつ外して必要性を確かめるところまでできた。原因を1つずつ止めて回し直すことで、性質ごとに何系統の原因があるかを数えられた。
- **つまずいた点**: 変数を足すたびに全動作の `UNCHANGED` を直す。活性の反例が長い。tla2tools 1.7.4 に `-dumpTrace json` がなく、テキストの反例を自作スクリプトで JSON に変えた。通しの実行は10コアで20〜30分。
- **読みやすさ**: 仕様は一番短いが、`/\` や `'` の記法に慣れていないとレビューしにくい。

## 何がわかったか

### 形式手法が効いたところ

- **「当たり前」を一文にすると、破れていた。** P1a・P1b は、コードを読めば誰もが成り立つと思う性質で、だからテストに書かれていなかった。
- **環境がしうることを列挙すると、試していない順序が出る。** 既存テストは人が思いついた筋を固定している。モデルでは「SDK はいつでもこのフレームを送りうる」と書くので、思いつかなかった順序も検査に入る。
- **「成立する」と言える。** P2（約束を忘れない）と P6（古いモード変更が効かない）は、過去に不具合があった箇所で、今は成り立つと全探索と証明で確かめられた。テストでは「見つからなかった」までしか言えない。
- **原因を切り分けられる。** FSL では、仮の修正を7つ全部入れると全安全性が証明でき、1つずつ外すと対応する性質だけが破れた。「ここを直せば、このモデルの範囲では安全性の反例が残らない」と言える。
- **設計の意図があいまいな箇所が見える。** P4 を書いたら、「一括拒否では通知しない」という既存の設計とぶつかった。性質を書く作業そのものが、仕様の確認になった。

### 効かなかったところ、限界

- **モデルが正しいかは別問題。** 8件のうち3件は SDK のふるまい次第で、モデル検査では決まらない。「SDK はこう動きうる」という仮定を人が確かめる必要がある。
- **仕様はコードと自動ではつながらない。** コードが変われば仕様は古くなる。Quint と TLA+ のトレース再生はその対策になりうるが、実装の private フィールドを覗く作りで、保守の手間がかかる。
- **出題が結果を左右する。** P4 を強く書きすぎたせいで M2 を素直に検出できなかった。性質の質は書き手に依存する。
- **安全性の反例は浅かった。** 今回は3〜7ステップで、ランダム実行でも足りた。全探索の力が要るほど深い不具合は、この範囲にはなかった。
- **コストは小さくない。** 数百行の対象に対して仕様は500〜750行、エージェントで2〜4時間。

### 使いどころ

向いているもの:

- 状態があり、外から順不同でイベントが届く部分。Bridge なら承認、入力キュー、再接続、セッションの開始と停止。
- 世代番号や「A のあとでないと B をしてはいけない」のような順序の制約がある部分。
- 過去に競合の不具合を直した部分。直したことを性質として固定できる。
- 3プロバイダ（Claude・Codex・Antigravity）で同じ性質が成り立つべき部分。性質を1回書けば、3実装を同じ基準で見られる。

向いていないもの:

- UI、CRUD、文字列の変換、パーサ。状態の組み合わせが問題にならない。
- 外部サービスのふるまいそのもの（SDK がどのフレームをいつ送るか）。仮定としてしか書けない。

## 採用後

2026-11-24、Quint を採用した。使い方は [formal/permission-flow/README.md](../formal/permission-flow/README.md) と [formal-check スキル](../.claude/skills/formal-check/SKILL.md) にある。

### 入れたもの

- **速い検査（`check.sh`、約2分）**: 型検査、ランダム実行、モデルから作ったトレース300本の実装への再生。CI の `Formal check` で、`formal/` か `sdk-process.ts` が変わったときに走る。
- **全探索（`full.sh`、約12分、手元で実行）**: TLC で到達できる全状態の安全性と、活性を調べる。Java が要る。
- **期待結果の一覧**: 破れることが期待される性質を記録し、増えても減っても検査が失敗する。今は仕込んだ退行だけが載っている。
- **Quint のバージョン固定**: `formal/quint.sh` の1か所。

FSL と TLA+ の成果物は `formal/permission-flow/evaluation/` に移し、保守していない。

### 直したもの

モデルを意図する動作に直す → 性質が成り立つことを確かめる → 再生テストが実装との食い違いを検出する → 実装を直す、の順で進めた。

| 疑い | 修正 | コミット |
|---|---|---|
| 4: 終了後の入力がキューに残る | `SdkProcess` は入力を捨て、入力ハンドラは `input_rejected` を返す | `6cc3f63a` |
| 1: status フレームが承認待ちを上書きする | 保留があるあいだは status フレームで状態を変えない | `22e1f952` |
| 2: 中止シグナルで通知も状態更新もない | 承認・拒否と同じ経路で決着させ、`permission_resolved` を送る | `22e1f952` |
| 3: 中止済みの要求を通知してから捨てる | 通知せずに拒否を返す | `22e1f952` |
| 5: 正常終了で保留が残る | 保留を拒否し、入力キューと入力待ちの状態を片付ける | `22e1f952` |
| 6: 正常終了 → 再開始 → 入力が消える | 同上（古い入力待ちが残らなくなった） | `22e1f952` |
| 8: `interrupt()` が承認待ちを抜けない | 拒否した要求を `permission_resolved` で知らせ、`running` にする | `22e1f952` |

- **疑い1・5は、本物の SDK で確かめずに防御的に直した。** 修正は数行で、SDK がその順で送らないなら何も起きない。
- **疑い8は既存テストの固定を変えた。** `interrupt` では通知しない、と固定していたテストを、通知する形に直した。`result`・`stop`・再開始は従来どおり通知しない。
- **疑い7は直していない。** ターンの外で承認要求が来る場合に、承認後の入力が渡らなくなる件。SDK がそう動くかが未確認で、直すには「承認待ちに入る前の状態へ戻す」設計の変更が要る。既知の違反として記録した。

### 直したあとの結果

- **安全性**: SDK の仮定12通りすべてで、11の性質が成立した。ランダム実行に加えて、TLC で全状態（インスタンスごとに約3.9万〜10.7万状態）を調べた。
- **活性**: 「承認要求はいずれ決着する」は調べた9通りすべてで成立。比較時点では、正常終了を許す仮定で破れていた。「入力はいずれ渡る」は、ターンの外の承認要求を許す3通りでだけ破れる（疑い7）。
- **仕込んだ退行**: 3つとも引き続き検出される。
- **実装との一致**: 修正後のモデルから作った300本が、修正後の `SdkProcess` と全ステップで一致した。1件目の修正では、モデルだけを直した段階で実装に流すと、300本中298本が食い違った。再生テストが食い違いを検出できることの確認になった。

出題時の性質のうち、「すべての要求に `permission_resolved` が届く」（P4 の厳しい読み）は検査から外した。`result`・`stop`・再開始は通知なしで要求を終わらせ、クライアントは状態の変化で表示を消す設計のため。代わりに、その規則を含めたクライアントの見え方（`P4_app`）を検査している。

### 本物の Claude セッションでの確認

テスト用 Bridge に WebSocket でつなぎ、ファイル作成の承認要求を出させて3通りを確かめた。届いた順は次のとおりで、どれも期待どおりだった。

| 操作 | 届いた順 |
|---|---|
| 承認待ち中に中断 | `waiting_approval` → `permission_request` → `running` → `permission_resolved` → `idle` |
| 承認 | `waiting_approval` → `permission_request` → `running` → `permission_resolved` → ツール実行 → `idle` |
| 拒否 | `waiting_approval` → `permission_request` → `running` → `permission_resolved` → `idle` |

アプリの画面（iOS シミュレーター）でも、承認と拒否の2通りを確かめた。どちらも承認バーが消え、セッションが待機状態に戻り、入力欄が使えるようになった。

承認待ち中の中断は、画面では確かめられなかった。Claude の承認待ち中は入力欄が承認バーに置き換わり、停止ボタンが出ないため（`apps/mobile/lib/features/claude_session/claude_session_screen.dart`）。今のアプリからはこの経路に入れないので、`interrupt()` の変更が効くのは、承認待ち中に中断を送るクライアントがある場合に限られる。

### まだ確かめていないこと

- 終了後の入力の拒否、SDK による要求の取り消し、ストリームの正常終了は、本物の SDK では起こせていない。確認は SDK の `query` を差し替えた単体テストと再生テストまで。
- 承認待ち中の中断の、アプリ側の見え方（上記の理由）。
- Bridge のリリースはしていない。
